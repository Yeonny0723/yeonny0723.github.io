# Career Description과 Portfolio 역할 분리 설계

## 목표

Career Description과 Portfolio가 같은 Agentic 문서 생성 경험을 반복 설명하지 않도록 역할과 깊이를 분리한다. 두 문서 모두 기능을 어떻게 만들었는지 설명하되, Career Description은 개인의 문제 해결과 기여를 검증하고 Portfolio는 대표 기능의 제품 설계·구현 과정을 증명한다.

## 문서별 책임

### Career Description

한 프로젝트를 텍스트 중심의 사례로 설명한다.

- 초기 기획에 없던 사용성·비기능 요구사항을 직접 제안한 배경
- 사용자가 기다림·중간 이탈·재진입·리뷰 범위에서 겪는 문제
- Agentic 멀티턴, 비동기 상태, 포맷별 operator 제한을 선택한 이유
- 본인이 담당한 구현 범위와 판단
- 생성 시간·비용·누락률 등 검증 가능한 결과
- 운영상 한계와 다음 개선점

세부 구현 용어는 사용하되, 용어 나열이 아니라 문제와 판단의 근거 안에서 설명한다.

### Portfolio

대표 프로젝트를 케이스 스터디로 설명한다.

- 사용자 문제와 직접 제안한 요구사항
- 생성 시작 → 이탈 → 재진입 → 결과 확인 → 누락 영역 리뷰 흐름
- Frontend, API, Agent Orchestrator, 추론 파이프라인, Worker, 결과 저장의 관계
- 필요한 단계만 선택하거나 구조 추론을 생략하는 Agent 의사결정 흐름
- 포맷별 operator와 문서 생성 문법을 통한 자율성 제한
- 비동기 상태 모델과 재진입 구조
- 누락 영역 표시를 통한 리뷰 범위 축소
- 품질·비용·지연시간 검증과 대표 성과

Portfolio에서는 `requestId`, Queue/Worker, Polling/Callback 등의 용어를 사용할 수 있지만, 단순 목록으로 나열하지 않고 사용자 흐름 또는 아키텍처 설명과 연결한다. 다른 프로젝트는 동일한 깊이로 확장하지 않고, 문서보안·AI·프론트엔드·보안·운영을 연결하는 개발 방식을 보여주는 짧은 사례로 배치한다.

## 중복 방지 원칙

| 내용 | Career Description | Portfolio |
| --- | --- | --- |
| 사용자 요구사항 | 내가 직접 제안한 배경과 판단 | 제품 흐름의 시작점 |
| Agentic 파이프라인 | 선택 이유와 구현 기여 | 단계 선택 구조와 동작 흐름 |
| 비동기 처리 | 재진입 요구를 해결한 기여 | 상태 전이·아키텍처로 시각화 |
| 결과 누락 표시 | 리뷰 부담을 줄인 결과 | 화면·데이터 흐름으로 증명 |
| 성과 수치 | 전체 수치와 검증 근거 | 대표 수치만 강조 |
| 기술 세부사항 | 개인이 직접 다룬 기술 | 구조 안에서 의미를 설명 |

## 수정 대상

- `portfolio/content/career/ai.md`: 요구사항 제안, 판단, 구현, 결과를 사례 중심으로 유지·보강한다.
- `portfolio/content/portfolio/ai-platform.md`: 문서 생성 기능을 대표 케이스 스터디로 확장하고 사용자 흐름·아키텍처·검증 구조를 중심으로 다시 쓴다.
- `portfolio/content/timeline.md`: 상세 구현을 반복하지 않고 대표 성과와 역할을 압축해 연결한다.
- `portfolio/content/resume/ai.md`: 이미 정리된 요구사항 주도성과 성과 수치를 유지하며 중복이 생기지 않는지 확인한다.

## 성공 기준

- Career Description을 읽으면 개인의 판단과 기여 범위를 설명할 수 있다.
- Portfolio를 읽으면 기능의 사용자 흐름과 실제 구현 구조를 설명할 수 있다.
- 두 문서에서 같은 문장을 복사하지 않고, 같은 사실이 서로 다른 증거 형태로 연결된다.
- 기존 디자인과 탭 구조를 변경하지 않는다.
- `yarn typecheck`, `yarn build`, `git diff --check`가 통과한다.
