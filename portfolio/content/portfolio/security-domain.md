# 보안 제품에서 배운 제품 개발

현재 회사에서 문서보안 협업 솔루션과 보안 교육·피싱 훈련 제품을 개발하며, 기능이 동작하는 것만큼 누가 어떤 권한으로 무엇을 볼 수 있는지가 중요하다는 기준을 갖게 되었습니다. 그래서 보안 요구를 마지막 검수 단계가 아니라 기획·도메인 설계·화면 구현·운영 환경을 관통하는 조건으로 봅니다.

## 제품 보안의 복잡성

- 고객사와 테넌트별로 제품 활성화·권한·설정이 달라지는 멀티테넌트 환경
- OTP/MFA와 Zero Trust를 포함한 인증 흐름
- DRM과 연결된 문서 권한 정책
- 훈련 메일·외부 콘텐츠를 화면에 표시할 때의 CSP와 DOM Sanitizing
- 문서 검색·생성 결과가 원문 근거와 제품의 보안 경계를 벗어나지 않도록 하는 검증
- npm 의존성·install script·lockfile처럼 개발 과정에서 제품 안정성에 영향을 줄 수 있는 공급망 위험

이런 환경에서는 프론트엔드에서 버튼을 숨기는 것만으로 충분하지 않습니다. API와 데이터 모델의 권한 경계, 실패했을 때의 기본 동작, 외부 콘텐츠를 표시하는 방식, 고객사별 운영 설정을 함께 확인해야 합니다. 복잡한 권한 정책은 화면·서버·데이터가 같은 기준을 공유해야 하며, 보안 실패가 발생해도 안전한 기본 동작과 재현 가능한 검증이 남아야 합니다.

## 제가 맡은 역할

M365 Web Add-in의 Graph API·테넌트 컨텍스트, Mind-SAT의 인증·교육·통계 흐름, 악성 메일 콘텐츠 정제, AI 서버 고가용성 구조를 개발했습니다. 보안 요구를 마지막 검수 단계가 아니라 도메인과 사용자 흐름을 설계하는 조건으로 다뤘습니다. 제품 보안과 팀 개발 환경의 보안은 목적이 다르지만, 둘 다 위험을 미리 나누고 자동 검증과 사람의 승인 경계를 함께 설계해야 한다는 점에서 연결됩니다.
