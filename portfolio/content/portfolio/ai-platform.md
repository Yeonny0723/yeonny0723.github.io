# Agentic 문서 생성을 검토 가능한 제품으로 만들기

반복 문서 생성 기능을 단순한 LLM 호출로 구현하면 사용자는 수 분 동안 화면을 기다려야 하고, 생성 중 이탈하면 작업을 잃거나 문서 전체를 다시 검토해야 합니다. 이 문제를 해결하기 위해 생성 중 재진입, 누락 영역 중심 리뷰, 불필요한 추론 단계 생략을 기능·비기능 요구사항으로 직접 제안하고, Agentic 멀티턴 실행·비동기 상태 관리·포맷별 operator·결과 검증을 하나의 제품 흐름으로 설계했습니다. 그 결과 필요한 경우에만 LLM을 호출하면서 생성 시간·비용·슬롯 누락률을 함께 낮출 수 있었습니다.

## 사용자가 경험하는 문서 생성 흐름

사용자 요청은 먼저 `requestId`로 접수하고, 실제 문서 생성은 백그라운드에서 진행합니다. 사용자가 화면을 떠나도 작업 상태와 결과를 저장해 두었다가 다시 진입할 수 있으며, 결과에는 누락 슬롯과 오류 위치를 함께 기록해 전체 문서가 아니라 필요한 부분만 리뷰하도록 했습니다.

```text
사용자 요청
    ↓
requestId 반환 → 백그라운드 생성 → 상태·결과 저장
    ↓                                      ↑
Agent 단계 선택 → 필요한 추론 실행      재진입·상태 조회
    ↓                                      ↑
문서 렌더링 → 누락 영역·오류 위치 확인 → 필요한 부분만 리뷰
```

API·worker·상태 저장소를 분리해 긴 작업이 API timeout에 묶이지 않도록 하고, 완료·실패·timeout·재시작 이후의 자원 정리까지 하나의 수명주기로 관리했습니다.

## 입력에 따라 달라지는 Agent 실행

docx·xlsx·pptx는 구조와 표현 단위가 다르지만 모든 요청에 같은 추론 순서를 적용할 필요는 없었습니다. 파일 구조 추론, 교체 영역 추론, 내용 추론, 렌더링을 독립 파이프라인으로 나누고 Agent가 입력과 목표를 분석해 필요한 단계만 멀티턴으로 선택하도록 구성했습니다.

```text
입력·목표 분석
      ├─ 단순 값 변환 → 구조 추론 생략 → 값 변환 → 렌더링
      └─ 구조 파악 필요 → 구조 추론 → 교체 영역 추론
                                      → 내용 추론 → 렌더링
```

이미 교체 위치가 정해진 단순 값 변환은 구조 추론을 건너뛰고, 원천 문서와 템플릿의 관계를 파악해야 하는 요청은 다음 추론 단계로 이어갑니다. 독립 단계는 병렬 처리하고 재사용 가능한 입력은 캐시해 LLM 호출 비용과 처리 시간을 줄였습니다.

## Agent의 자율성과 실행 경계

LLM에는 필요한 추론 단계와 생성 내용을 판단하는 역할을 맡기되, 실제 문서 변경은 포맷별로 정의한 operator와 문서 생성용 문법을 통해서만 실행되도록 했습니다. Agent가 임의의 문서 조작 코드를 만들지 못하게 하면서도 입력에 따라 작업 순서를 선택할 수 있게 한 구조입니다. 자율 판단 영역, 프로그램이 검증하는 실행 영역, 사용자가 확인하는 리뷰 영역을 분리해 AI의 유연성과 제품의 안전성을 함께 확보했습니다.

## 품질·비용·운영 검증

청킹 전략과 모델·프롬프트 조합을 같은 문서 기준 데이터로 비교하고, 모델별 input/output token 단가와 실제 사용량으로 호출 비용을 계산했습니다. 문서 생성 결과는 누락 슬롯과 오류 위치를 구분해 내부 검증·QA 대상까지 확인할 수 있게 했습니다.

- 생성 시간: 4~5분 → 1~2분 수준
- 문서 1건 평균 비용: 약 350원 → 100원 수준
- 슬롯 누락률: 약 20% → 2% 수준

## 검색·AI 서비스·개발 도구로 확장한 기준

Wrapsody AI 문서 검색은 36개 golden dataset을 기준으로 expected document/span, Text2SQL, 문서 검색, 최종 RAG 응답을 분리해 평가했습니다. Playwright로 여러 테스트 서버에서 같은 질문을 반복 실행하고 다의어·동의어 실패 로그를 검색과 prompt 개선으로 연결했습니다.

Mind-SAT AI Python 백엔드에는 OpenAI SDK·LangChain 기반 메일 템플릿 추천·생성과 보안 퀴즈 생성 기능을 연결했으며, AI 서버는 OCI Instance Pool과 Private Load Balancer로 장애 복구 구조를 구성했습니다. 사내 디자인 시스템은 TypeScript AST·Storybook·JSDoc·디자인 토큰을 MCP 조회 구조로 바꿔 AI가 실제 컴포넌트 기준을 참고하게 했습니다.

개인 프로젝트 `agent-orchestration`에서는 같은 원칙을 개발 과정에 적용해 작업 규모에 따라 spec 승인·TDD·테스트 검증·PR 작성 절차를 다르게 실행하고, Claude Code와 Codex의 차이는 plugin adapter로 감쌌습니다. AI를 호출하는 기능보다 중요한 것은 어떤 판단을 위임하고 어디에서 검증과 사람의 승인을 남길지 설계하는 일이라고 생각합니다.
