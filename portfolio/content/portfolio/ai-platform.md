# Agentic 문서 생성을 검토 가능한 제품으로 만들기

반복 문서 생성 기능을 단순한 LLM 호출이 아니라, 사용자가 기다림·재진입·리뷰 부담을 관리할 수 있는 제품 흐름으로 설계했습니다. 이 프로젝트에서 중요한 점은 정해진 기획을 구현한 것이 아니라, 실제 사용 상황을 기준으로 기능 요구사항과 비기능 요구사항을 직접 제안했다는 것입니다.

## 1. 사용자의 작업 방식을 제품 요구사항으로 정의하기

문서 생성에는 수 분이 걸릴 수 있으므로 사용자가 결과를 기다리며 화면을 계속 보고 있어야 하면 업무 흐름이 끊깁니다. 또한 생성 중 다른 업무로 이동했다가 돌아왔을 때 작업이 사라지거나, 문서 전체를 다시 확인해야 한다면 자동화의 효과가 줄어듭니다.

그래서 다음 요구사항을 문서 생성 기능의 기준으로 제안했습니다.

| 구분 | 요구사항 | 제품에 반영한 방식 |
| --- | --- | --- |
| 기능 | 생성 중 화면을 떠나도 다시 작업을 확인할 수 있어야 함 | `requestId` 기반 작업 상태 조회와 재진입 흐름 |
| 기능 | 추론이 누락된 부분만 리뷰할 수 있어야 함 | 누락 슬롯·오류 위치·리뷰 대상 표시 |
| 기능 | 입력에 따라 불필요한 추론 단계를 실행하지 않아야 함 | Agent의 단계 선택과 조건부 파이프라인 실행 |
| 비기능 | 긴 작업이 API timeout에 영향을 주지 않아야 함 | 비동기 요청·백그라운드 실행·상태 저장 |
| 비기능 | Agent가 임의의 문서 조작을 실행하지 않아야 함 | 포맷별 허용 operator와 문서 생성 문법 |
| 비기능 | 품질·비용·처리 시간을 함께 확인할 수 있어야 함 | golden dataset·token cost·처리 시간 기준 |

## 2. 사용자가 경험하는 흐름

문서 생성 요청을 접수하는 순간부터 결과를 리뷰하는 단계까지를 하나의 제품 흐름으로 연결했습니다.

```text
사용자 요청
    ↓
requestId 즉시 반환 ─────────────┐
    ↓                            │
Agent가 입력과 목표 분석          │ 사용자가 화면을 떠남
    ↓                            │
필요한 파이프라인만 멀티턴 실행    │
    ↓                            │ 다시 진입해 상태 조회
결과·누락 영역·오류 위치 저장  ←──┘
    ↓
필요한 부분만 리뷰하고 문서 확정
```

API는 접수 번호를 먼저 반환하고, 백그라운드 작업이 생성·상태 갱신·결과 저장을 담당합니다. 화면은 같은 상태 저장소를 기준으로 진행·완료·실패·timeout을 확인하며, 중단된 작업은 재시작 후 남은 자원을 정리할 수 있습니다.

## 3. Agent가 필요한 단계만 선택하도록 구성하기

문서 포맷마다 구조와 표현 단위가 다르지만, 모든 요청에 구조 추론부터 실행할 필요는 없었습니다. 파일 구조 추론, 교체 영역 추론, 내용 추론, 렌더링을 독립적인 파이프라인으로 나누고 Agent가 현재 입력과 목표에 필요한 단계만 선택하도록 했습니다.

```text
입력·목표 분석
      ├─ 단순 값 변환 → 구조 추론 생략 → 값 변환 → 렌더링
      └─ 구조 파악 필요 → 구조 추론 → 교체 영역 추론
                                      → 내용 추론 → 렌더링
```

예를 들어 이미 교체 위치가 정해진 단순 값 변환에는 구조 추론을 실행하지 않습니다. 반대로 원천 문서와 템플릿의 관계를 먼저 파악해야 하는 요청에는 다음 단계의 추론을 이어서 호출합니다. 이 방식으로 필요한 경우에만 LLM을 호출하고, 단계 내 독립 작업은 병렬 처리하며, 재사용 가능한 입력은 캐시했습니다.

## 4. 자율성을 허용하되 실행 범위를 제한하기

Agent에게 문서 조작 코드를 직접 만들게 하면 다양한 문서를 처리할 수 있지만, 임의 코드 실행과 실패 원인 추적 문제가 생깁니다. 따라서 LLM은 “어떤 작업을 할지” 판단하고, 실제 문서 변경은 포맷별로 정의한 operator와 문서 생성용 문법을 통해서만 실행되도록 경계를 나눴습니다.

- **판단 영역**: 필요한 추론 단계, 교체 대상, 생성 내용
- **실행 영역**: 허용된 operator, 포맷별 렌더러, 검증 규칙
- **리뷰 영역**: 누락 슬롯, 오류 위치, 사용자가 확인해야 할 결과

이 구조는 Agent의 자율성을 없애는 방식이 아니라, 자율적으로 판단할 수 있는 범위와 프로그램이 검증해야 하는 범위를 분리하는 방식입니다.

## 5. 품질·비용·운영을 함께 검증하기

청킹 전략과 모델·프롬프트 조합을 같은 문서 기준 데이터로 비교하고, 모델별 input/output token 단가와 실제 사용량으로 호출 비용을 계산했습니다. 문서 생성 결과는 누락 슬롯과 오류 위치를 구분해 내부 검증·QA가 필요한 지점을 확인할 수 있게 했습니다.

- 생성 시간: 4~5분 → 1~2분 수준
- 문서 1건 평균 비용: 약 350원 → 100원 수준
- 슬롯 누락률: 약 20% → 2% 수준

이 경험을 통해 AI 기능의 품질을 모델 응답만으로 판단하지 않고, 사용자가 얼마나 기다리는지, 다시 들어왔을 때 작업을 이어갈 수 있는지, 어디를 리뷰해야 하는지까지 포함해 제품 품질로 관리하게 되었습니다.

## 검색과 평가

Wrapsody AI 문서 검색은 36개 golden dataset을 기준으로 expected document/span, Text2SQL, 문서 검색, 최종 RAG 응답을 분리해 평가했습니다. Playwright로 여러 테스트 서버에서 같은 질문을 반복 실행하고, 다의어·동의어 실패 로그를 검색 개선과 prompt 개선으로 연결했습니다.

## AI 기능의 제품화와 운영

Mind-SAT AI Python 백엔드에는 OpenAI SDK·LangChain 기반 메일 템플릿 추천·생성과 보안 퀴즈 생성 기능을 연결했습니다. 단일 AI 서버의 장애 위험은 OCI Instance Pool과 Private Load Balancer로 줄이고, 실제 인스턴스 중지 테스트로 장애 복구를 검증했습니다.

## 개발 시스템에도 같은 기준 적용하기

사내 디자인 시스템을 AI Agent가 조회할 수 있도록 TypeScript AST·Storybook·JSDoc·디자인 토큰을 구조화하고 MCP 서버를 만들었습니다. AI가 임의의 UI 규칙을 생성하는 대신 실제 컴포넌트와 사용 기준을 조회하게 해, 제품 개발에서 사용한 “자율성은 허용하되 검증 가능한 범위 안에서 실행한다”는 원칙을 개발 도구에도 적용했습니다.

개인 프로젝트 `agent-orchestration`에서는 이 원칙을 개발 과정으로 확장했습니다. 작업 규모에 따라 spec 승인·TDD 구현·테스트 검증·PR 작성 절차를 다르게 적용하고, Claude Code와 Codex의 차이는 plugin adapter로 감싸 공통 skill에서 판단 기준을 유지했습니다.
