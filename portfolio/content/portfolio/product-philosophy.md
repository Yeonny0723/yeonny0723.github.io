# 제품을 만드는 방식

팀과 제품의 성장을 우선하고, 배우고 공유하는 문화를 즐기며, 호기심을 바탕으로 업무의 경계를 넓혀 왔습니다. 제가 만드는 제품은 프론트엔드·백엔드·AI 중 하나의 레이어에 머물지 않습니다. 사용자가 실제로 완료하려는 일에서 출발해 화면의 상태, 도메인과 데이터, 비동기 작업, 권한과 보안, 테스트와 배포까지 연결합니다.

## 복잡성을 다루는 기준

### Frontend — 사용성과 변경 가능성

복잡한 상태와 비즈니스·도메인·UI 로직을 기능 단위로 나눕니다. 사용자가 끝까지 완료할 수 있는 흐름을 먼저 설계하고, 모노레포·디자인 시스템·공통 라이브러리로 반복 개발의 속도와 일관성을 높입니다. Playwright E2E로 정상 흐름뿐 아니라 여러 사용자와 실패 상태까지 반복 검증합니다.

### Backend / Domain — 낮은 결합과 안전한 변화

레거시와 하위 호환을 고려해 고객사 운영 환경에 영향을 주는 변경 범위를 좁힙니다. 도메인 경계를 낮은 결합으로 나누고, MSSQL 쿼리·트랜잭션·동시성·timeout·retry·부분 실패를 하나의 데이터 흐름으로 판단합니다. 내부 작업이 실패해도 제품 전체가 무너지지 않고 빠르게 실패하거나 다시 처리될 수 있어야 한다고 봅니다.

### AI Application — 불확실성을 운영 기준으로 바꾸기

LLM에 위임할 작업과 코드·규칙이 책임질 작업을 구분합니다. 비동기 API·Queue/Worker·Polling·Callback·Cleanup Scheduler로 긴 작업의 상태와 자원을 관리하고, 평가셋으로 검색·RAG·Text2SQL과 문서 생성 품질을 비교합니다. 모델·프롬프트·청킹 기준은 품질뿐 아니라 지연시간·비용·캐시 적중까지 함께 보고 선택합니다.

### Product Operations — 보안을 처음부터 제품 조건으로 보기

보안은 마지막 검수 항목이 아니라 기획과 개발 단계에서 함께 결정해야 하는 제품 조건입니다. 인증·권한·멀티테넌트·Zero Trust·DRM 정책·외부 콘텐츠 처리·고가용성·장애 복구를 사용자 흐름과 연결해 봅니다. 제품 기능과 팀 개발 환경의 공급망 보안도 구분하되, 각각의 경계와 사람 검토 지점을 명확히 둡니다.

## 제가 반복해서 확인하는 질문

1. 사용자가 실제로 완료하려는 일은 무엇인가?
2. 복잡성을 어느 도메인·기능·서비스 단위로 나누어야 변경 범위를 줄일 수 있는가?
3. 어느 판단을 LLM에 위임하고, 어느 판단을 코드와 운영 기준이 책임져야 하는가?
4. 실패했을 때 어디서 멈췄고, 어떻게 재현·복구·검증할 수 있는가?

프론트엔드의 사용성, 백엔드의 안정성, AI의 가능성과 운영 효율은 서로 떨어진 체크리스트가 아니라 하나의 제품 흐름입니다. 이 경계가 만나는 곳에서 실제로 동작하고 계속 개선할 수 있는 제품을 만듭니다.
