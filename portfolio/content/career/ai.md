# AI Engineer Career Description

## 1. Agentic 템플릿 기반 문서 생성

### 한 줄 요약

반복 문서 작성 문제를 필요한 단계만 선택하는 Agentic·비동기 LLM 파이프라인으로 바꿔, 생성 시간·비용·슬롯 누락을 함께 줄였습니다.

### 배경과 문제

템플릿 문서와 여러 원천 파일을 받아 보고서·신청서·검토서·제안서 형태의 새 문서를 만드는 기능이 필요했습니다. 초기 기획은 문서 생성 자체에 집중했지만, 사용자가 수 분 동안 화면을 붙잡지 않고 중간에 이탈했다가 다시 들어와도 작업을 이어가며 추론이 누락된 부분만 확인할 수 있어야 한다고 판단해 사용성·운영 요구사항을 직접 제안했습니다. docx·xlsx·pptx는 표현 단위가 서로 달랐고, 모든 문서에 동일한 파이프라인을 실행하면 필요하지 않은 LLM 호출과 처리 시간이 발생했습니다. 긴 문서를 LLM에 한 번에 넘기면 슬롯 누락도 반복되었습니다.

### 제가 제안한 요구사항과 판단 기준

기능 요구사항으로는 생성 중 이탈 후 재진입, 진행 상태 확인, 누락 슬롯·오류 위치 표시를 제안했습니다. 비기능 요구사항으로는 긴 작업이 API timeout을 일으키지 않을 것, 불필요한 LLM 호출을 줄일 것, Agent가 허용된 문서 조작 범위를 벗어나지 않을 것을 기준으로 삼았습니다. LLM이 문서 조작 코드를 직접 만들게 하면 표현력은 높지만 임의 코드 실행 위험과 실패 원인 추적 문제가 생겼고, 구조 추론이 필요 없는 값 변환에도 전체 단계를 실행하면 4~5분의 처리 시간과 불필요한 비용이 발생할 수 있었습니다.

### 판단과 구현

파일 구조·교체 영역·내용 추론과 렌더링을 여러 파이프라인으로 나누고, Agent가 멀티턴으로 현재 입력에 필요한 단계만 선택·실행하게 했습니다. 구조 추론이 필요 없는 단순 값 변환은 해당 단계를 건너뛰고, 필요한 경우에만 다음 추론 파이프라인을 호출하도록 해 LLM 호출 비용과 처리 시간을 줄였습니다. 사용자가 생성 중 화면을 떠나도 다시 작업에 들어올 수 있도록 `requestId`를 즉시 반환하고 Queue·Worker가 백그라운드에서 생성·상태 갱신·결과 저장을 담당하게 했습니다. 추론 결과에 누락된 슬롯과 오류 위치를 함께 기록해 필요한 리뷰 포인트만 확인할 수 있게 했습니다. 청킹 전략과 모델·프롬프트 조합은 기준 데이터로 비교하고, 문서 생성용 문법과 docx·xlsx·pptx 포맷별 허용 연산자를 제한해 Agent의 자율성이 실행 범위를 벗어나지 않게 했습니다. Polling과 Callback은 같은 상태 저장소를 읽게 하고, 완료·실패·timeout·재시작 뒤에는 Cleanup Scheduler가 작업 자원을 회수하도록 했습니다.

### 결과와 검증

- 생성 시간: 4~5분 → 1~2분 수준
- 슬롯 누락률: 약 20% → 2% 수준
- 문서 1건 평균 비용: 약 350원 → 100원 수준

### 운영 기반

상태를 `queued → running → success / fail`로 관리하고, 사용자가 결과와 수동 리뷰 지점을 확인할 수 있게 했습니다. 문서보안 제품의 특성상 LLM이 실행 가능한 임의 코드를 만들지 못하도록 문법의 허용 범위를 제한했습니다.

### 한계와 다음 단계

문서 포맷별 구조와 슬롯 기준은 계속 확장해야 합니다. 포맷별 누락 사례를 평가셋에 유지하고, 새 연산자를 추가할 때는 허용 범위와 렌더러 검증을 함께 갱신하는 기준을 둡니다. 모델과 프롬프트 조합을 바꿀 때도 품질만 보지 않고 비용·지연시간·캐시 적중을 함께 비교해야 한다는 기준을 세웠습니다.

## 2. 검색·RAG·Text2SQL 품질 평가 체계

### 한 줄 요약

LLM 답변만 보는 대신 검색 결과·근거 span·최종 응답을 분리해 비교할 수 있는 평가 흐름을 구성했습니다.

### 배경과 문제

Wrapsody AI 문서 검색에서는 다의어·동의어 때문에 사용자의 질문과 문서 표현이 달랐고, RAG 응답이 올바른 문서 근거를 사용했는지 확인할 기준이 필요했습니다. Text2SQL, 문서 검색, 최종 답변을 한 번에 평가하면 실패 지점을 구분하기 어려웠습니다.

### 제약과 선택지

수동으로 질문을 입력하는 방식은 빠르게 시작할 수 있지만 개선 전후 비교가 어렵습니다. 검색 로그만 보는 방식은 실패 패턴은 보여주지만 기대 결과와의 차이를 정량적으로 관리하기 어렵습니다.

### 판단과 구현

expected document/span과 기대 답변 기준을 정의한 36개 golden dataset을 구성했습니다. Playwright로 여러 테스트 서버에서 같은 질문을 반복 실행하고, Text2SQL 결과·문서 검색 결과·최종 RAG 응답을 각각 기대 결과와 비교했습니다. 검색된 문서 근거, 답변 형식, fallback 정책을 prompt 정책과 함께 관리했습니다.

### 결과와 검증

검색 품질을 주관적 판단이 아니라 expected document/span 대비 실제 결과로 비교할 수 있게 했습니다. 로컬 모델 변경 전후를 같은 36개 평가셋으로 확인하고, 다의어·동의어 실패 로그를 prompt 보강과 검색 개선 대상으로 연결했습니다.

### 한계와 다음 단계

현재 평가셋은 제품의 대표 질의를 중심으로 구성되어 있으므로, 운영 로그에서 새 실패 패턴을 수집해 난이도 축과 기대 결과를 계속 보강해야 합니다.

## 3. AI 기능의 제품화와 운영 안정화

Mind-SAT AI의 Python 백엔드에서 OpenAI SDK·LangChain 기반 메일 템플릿 추천·생성과 보안 퀴즈 생성 기능을 개발했습니다. 산업군·부서·직급·기술 이해도·위협 수준·메일 유형을 prompt 컨텍스트로 구조화하고, 생성 결과를 프론트엔드에서 안전하게 표시하도록 sanitize 처리를 적용했습니다. LLM 요청처럼 응답 시간이 긴 작업은 Python 서버의 동시성·비동기 처리 관점에서 검토해 사용자 요청과 백그라운드 작업의 책임을 나눴습니다.

단일 인스턴스 장애로 AI 기능 전체가 중단되는 문제에는 OCI Instance Pool 2대와 Private Load Balancer를 적용했습니다. 애플리케이션 변경을 최소화한 채 장애 인스턴스 제외·신규 인스턴스 보충·Health Check를 구성하고, 인스턴스 중지 테스트로 복구 동작을 확인했습니다.

## 4. AI를 개발 시스템에 연결하기

사내 디자인 시스템을 AI Agent가 조회할 수 있도록 TypeScript AST·Storybook·JSDoc·디자인 토큰을 `generated-registry.json`으로 구조화하고 MCP 서버를 만들었습니다. 공통 컴포넌트의 존재 여부와 props·훅·색상·아이콘 사용 규칙을 조회 가능한 정보로 바꿔, AI가 임의의 UI 규칙을 생성하는 위험을 줄였습니다.

## 5. Agentic AI 개발 흐름과 기술 표준

개인 프로젝트 `agent-orchestration`에서는 AI Agent가 작업 규모 판정부터 spec 승인, TDD 구현, 테스트 민감도 검증, PR 작성까지 일관된 절차로 수행하도록 하네스를 설계했습니다. Claude Code와 Codex의 차이는 얇은 plugin adapter로 감싸고, 실제 판단과 검증 기준은 공통 skill로 유지했습니다.

모든 작업에 같은 절차를 강제하지 않도록 작업 규모에 따라 기획 깊이와 승인 경계를 달리하고, 결함 주입으로 테스트가 실제로 회귀를 감지하는지 확인하는 단계를 넣었습니다. 이 경험을 통해 AI 기능 자체뿐 아니라 AI가 제품과 개발 과정에서 어떤 기준으로 행동해야 하는지도 설계하게 되었습니다. 가드레일은 AI의 자율성을 막는 장치가 아니라 review point를 줄이면서도 사람이 판단해야 할 경계를 분명히 하는 운영 기준으로 보게 되었습니다.
