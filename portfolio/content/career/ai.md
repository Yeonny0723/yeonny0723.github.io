# AI Engineer Career Description

## 1. Agentic 템플릿 기반 문서 생성

템플릿 문서와 여러 원천 파일을 결합해 보고서·신청서·검토서·제안서를 만드는 기능을 개발하면서, 문서를 한 번에 생성하는 것보다 사용자가 긴 작업 중 화면을 떠났다가 다시 들어와도 결과를 이어서 확인하고 추론이 누락된 부분만 검토할 수 있어야 한다는 요구사항을 먼저 세웠습니다. 특히 docx·xlsx·pptx는 표현 단위가 서로 다르고 문서마다 필요한 처리 단계도 달랐기 때문에, 모든 입력에 같은 LLM 파이프라인을 적용하면 비용과 시간이 늘어나는 동시에 긴 문서에서 슬롯 누락이 반복될 수 있었습니다.

이 요구를 충족하기 위해 파일 구조·교체 영역·내용 추론·렌더링을 독립적인 파이프라인으로 나누고, Agent가 멀티턴으로 현재 문서에 필요한 단계만 선택하도록 구성했습니다. 구조 추론이 필요 없는 값 변환은 해당 단계를 건너뛰고 필요한 경우에만 다음 파이프라인을 호출해 불필요한 LLM 호출을 줄였으며, 문서 포맷별 허용 연산자를 별도로 두어 Agent가 임의의 문서 조작 코드를 실행하지 못하게 했습니다. 생성 요청에는 `requestId`를 즉시 발급하고 Queue·Worker가 백그라운드에서 생성·상태 갱신·결과 저장을 담당하도록 해 API timeout을 피했으며, Polling과 Callback은 같은 상태 저장소를 바라보게 구성했습니다. 결과에는 누락 슬롯과 오류 위치를 함께 기록해 사용자가 전체 문서를 다시 읽지 않고 필요한 부분만 리뷰할 수 있게 했고, 완료·실패·timeout·재시작 뒤에는 Cleanup Scheduler가 작업 자원을 회수하도록 했습니다.

청킹 전략과 모델·프롬프트 조합은 기준 데이터로 비교하고, 새 문서 연산자를 추가할 때는 허용 범위와 렌더러 검증을 함께 갱신하는 방식으로 품질과 보안을 관리했습니다. 그 결과 생성 시간은 4~5분에서 1~2분 수준으로, 문서 1건의 평균 비용은 약 350원에서 100원 수준으로 줄었고, 슬롯 누락률은 약 20%에서 2% 수준으로 낮아졌습니다.

## 2. 검색·RAG·Text2SQL 품질 평가 체계

Wrapsody AI 문서 검색에서는 사용자의 질문과 문서 표현이 다의어·동의어로 어긋날 수 있었고, Text2SQL 변환부터 검색된 문서 근거, 최종 RAG 답변까지 어느 단계에서 품질이 떨어졌는지 구분할 기준이 필요했습니다. 수동 질의나 검색 로그만으로는 모델과 프롬프트 변경 전후를 같은 조건에서 비교하기 어려웠기 때문에, expected document/span과 기대 답변을 포함한 36개 Golden Dataset을 구성했습니다.

Playwright로 여러 테스트 서버에 같은 질문을 반복 실행하고 Text2SQL 결과·문서 검색 결과·최종 응답을 각각 기대 결과와 비교하도록 평가 흐름을 만들었습니다. 이를 통해 LLM 답변의 인상만으로 품질을 판단하지 않고 검색 근거와 답변 형식을 분리해 확인할 수 있었으며, 다의어·동의어 실패 로그를 prompt 보강과 검색 개선으로 연결했습니다. 운영 로그에서 새 실패 패턴을 수집해 평가셋의 난이도와 기대 결과를 계속 보강하는 것을 후속 기준으로 두고 있습니다.

## 3. AI 기능의 제품화와 운영 안정화

Mind-SAT AI에서는 산업군·부서·직급·기술 이해도·위협 수준·메일 유형에 따라 달라지는 보안 훈련 콘텐츠를 만들 수 있도록 Python 백엔드에 OpenAI SDK·LangChain 기반 메일 템플릿 추천·생성과 보안 퀴즈 생성 기능을 개발했습니다. 입력 조건을 prompt 컨텍스트로 구조화하고 생성 결과를 안전하게 표시하도록 sanitize 처리를 적용했으며, 응답 시간이 긴 LLM 요청은 동시성·비동기 처리 관점에서 사용자 요청과 백그라운드 작업의 책임을 나누어 설계했습니다.

AI 기능이 단일 인스턴스 장애로 함께 중단되지 않도록 OCI Instance Pool 2대와 Private Load Balancer를 적용하고, 장애 인스턴스 제외·신규 인스턴스 보충·Health Check를 구성했습니다. 인스턴스 중지 테스트로 복구 동작을 확인해 기능 개발에 그치지 않고 운영 중 장애를 감당할 수 있는 배포 구조까지 연결했습니다.

## 4. AI를 개발 시스템에 연결하기

사내 디자인 시스템을 AI Agent가 조회하고 기존 규칙 안에서 화면을 만들 수 있도록 TypeScript AST·Storybook·JSDoc·디자인 토큰을 `generated-registry.json`으로 구조화하고 MCP 서버를 만들었습니다. 공통 컴포넌트의 존재 여부와 props·훅·색상·아이콘 사용 규칙을 조회 가능한 정보로 바꾸어, AI가 임의의 UI 규칙을 생성하는 위험을 줄이면서 개발자가 검토할 수 있는 근거를 남겼습니다.

## 5. Agentic AI 개발 흐름과 기술 표준

개인 프로젝트 `agent-orchestration`에서는 AI Agent가 작업 규모를 먼저 판정하고, 필요한 수준의 spec 승인·TDD 구현·테스트 민감도 검증·PR 작성까지 이어가도록 개발 하네스를 설계했습니다. Claude Code와 Codex의 차이는 얇은 plugin adapter로 감싸고 실제 판단과 검증 기준은 공통 skill로 유지했으며, 모든 작업에 같은 절차를 강제하지 않도록 규모에 따라 기획 깊이와 승인 경계를 달리했습니다.

결함 주입으로 테스트가 실제 회귀를 감지하는지 확인하는 단계까지 포함하면서, AI 기능 자체뿐 아니라 AI가 제품과 개발 과정에서 어떤 기준으로 행동해야 하는지도 설계하게 되었습니다. 이 경험을 통해 가드레일을 자율성을 막는 장치가 아니라 사람의 review point를 줄이면서도 반드시 사람이 판단해야 할 경계를 분명히 하는 운영 기준으로 바라보게 되었습니다.
