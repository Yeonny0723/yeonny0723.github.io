## 회사와 제품

Fasoo AI에서 기업용 보안 제품의 AI 기능과 운영 환경을 개발했습니다. Wrapsody는 기업 문서를 암호화하고 문서별 권한과 버전을 관리하는 서비스로, 사내 운영 환경에만 약 100만 건의 문서가 축적돼 있고 약 10여 고객사에 클라우드·온프레미스로 제공됩니다. 회사 제품은 고객사별 서버 환경, 복잡한 문서 권한, 암·복호화를 고려해야 한다는 특성이 있습니다. Mind-SAT은 31개 고객사·19,790명이 사용하는 피싱 훈련·보안교육 SaaS로, 훈련 메일 분석과 메일 템플릿·퀴즈 생성에 AI를 활용합니다.

## AI 제품 개발 · 2025–현재

### Wrapsody 문서 생성 Agent | 2026–현재 · 메인 개발

템플릿 문서와 여러 원천 파일을 넣으면 양식을 채운 DOCX·XLSX·PPTX를 만들어 주는 Agent입니다. 보고서·신청서처럼 양식은 같고 회차별·고객별 데이터만 바뀌는 반복 문서 작업을 줄이기 위해 만들었습니다.

**문제와 제약**

- 문서마다 문단·셀·도형 구조가 달라, 자연어 요구를 실제 파일 변경으로 옮기려면 단계별 계획이 필요했습니다. 요구 자체가 처음부터 구체적이지 않은 경우도 많았습니다.
- 긴 문서를 한 번에 넘기면 추론해야 할 영역이 너무 많아 정확도가 떨어지고 추론에 실패했습니다.
- 모델이 만든 코드를 실행해야 하는데, 문서 보안 제품의 처리 경계를 벗어나면 안 됐습니다. 사용자 지침뿐 아니라 원천 파일과 템플릿 안에도 데이터 유출을 유도하는 Prompt Injection이 숨어 있을 수 있었습니다.
- 문서 생성까지 전체 파이프라인이 최대 10분까지 걸릴 수 있어 사용성을 해쳤고, 요청을 붙잡고 기다리는 동기 처리로는 동시 요청 격리와 재접속이 어려웠습니다.

**판단과 구현**

- 모델이 문서 전체를 임의로 고치지 않도록 구조 분석 → 변경 영역 확인 → 변경 계획 → 코드 생성 → 실행 → 렌더링 → 보안 검증으로 단계를 나누고, 규칙으로 결정할 수 있는 전처리·렌더링에는 LLM을 쓰지 않았습니다. 요구가 불명확하면 바로 실행하지 않고 역질문으로 대상·범위·출력 형식부터 좁힙니다.
- 문서 구조를 기준으로 청킹을 도입하고 여러 크기를 시험한 끝에 8,000자를 택했습니다. 이보다 작게 자르면 테이블 안의 추론 영역이 잘려 오히려 실패했기 때문입니다.
- GPT-5.6 Luna·Terra·Sol을 정확도와 비용으로 비교해, 가장 저렴한 Luna로도 목표 정확도를 맞출 수 있음을 확인하고 채택했습니다.
- 생성 코드를 애플리케이션 서버에서 실행하면 보안 경계와 외부 네트워크를 통제하기 어려워, OpenAI Code Interpreter 샌드박스와 Network Policy로 격리했습니다. 실행이 한 번에 성공한다고 가정하지 않고, 오류를 모델에 되돌려 코드를 재생성하는 루프를 두었습니다.
- 입력과 결과물 모두 신뢰하지 않는다는 전제로, 실행 전에는 입력 전반의 Prompt Injection을 검사하고 결과 Office 파일은 ZIP/XML로 풀어 Macro·VBA·ActiveX·OLE·외부 참조를 검사합니다.
- Spring Boot·MySQL이 세션과 작업 상태를, Python 서버가 문서 처리를 맡도록 책임을 나누고, 문서 생성 전용 스레드 풀 워커로 분리해 비동기로 처리하며 SSE로 단계별 상태를 전달했습니다.

**결과**

- 청킹 도입으로 추론 대상 영역 대비 추론 성공률이 약 20% 높아졌고, 모델 비교로 Sol 대비 비용을 약 1/10로 줄였습니다.
- 사용자가 화면을 닫았다 돌아와도 세션·상태·결과를 이어서 확인할 수 있고, 채워지지 않은 위치·실행 오류·보안 검사 결과가 함께 제공돼 다시 볼 지점을 바로 알 수 있습니다.

### Wrapsody AI 검색·응답 평가 체계 | 2026–현재 · 평가 체계 담당

RAG·Text2SQL 기능 개발에는 지원 역할로 참여했고, 그중 품질을 판단하는 평가 체계 구축과 Text2SQL 시멘틱 레이어 개선을 맡았습니다.

**문제와 제약**

- 사용자 질문에는 동의어·다의어가 섞여 있어, 같은 의도라도 검색어와 문서 표현이 달라 기대 문서를 놓쳤습니다.
- 최종 답변만 보면 실패가 Text2SQL·검색·생성 중 어디서 났는지 알 수 없었고, 로컬 LLM의 모델과 파라미터가 계속 바뀌는 상황이었습니다.

**판단과 구현**

- 수동 확인이나 로그만으로는 개선 전후를 비교할 수 없어, 질문마다 찾아야 할 문서·본문 위치·답변을 미리 정해 둔 정답 기준 평가셋을 사양·동의어·모호한 표현·시간축 난이도별 36개 질문으로 만들었습니다.
- 실패 위치를 가르기 위해 Text2SQL·문서 검색·최종 응답을 단계별로 따로 평가하고, Playwright로 여러 테스트 서버에서 같은 시나리오를 반복 실행하도록 자동화했습니다.

**결과**

- 평가에서 드러난 동의어·다의어 오류를 시멘틱 레이어(동의어 사전·컬럼 설명) 보강으로 해결해 정답을 20/36에서 36/36으로 높였습니다.
- 모델이 바뀌어도 같은 기준으로 비교할 수 있게 되었고, 동일 조건에서 Gemma 4 26B-A4B와 Qwen3.5-27B(FP8, RTX 5090)를 비교해 Qwen3.5의 상대 시간 표현·파일 유형 질의 실패를 확인했습니다.

### Mind-SAT 보안 훈련 콘텐츠 생성 Agent | 2026 · 4인 TF 중 AI 메인 개발

31개 고객사·19,790명이 쓰는 피싱 훈련 제품에, 고객사 맞춤 훈련 메일과 보안 퀴즈를 생성하는 멀티턴 Agent를 Python·OpenAI SDK·LangChain으로 개발했습니다.

**문제와 제약**

- 훈련 담당자는 신고된 실제 메일을 훈련 템플릿으로 재사용하는데, AI로 사용 가능 여부를 확인한 뒤에도 샌드박스에서 메일을 직접 열고 HTML 태그와 링크를 하나씩 열어 위협 여부를 판단해야 했습니다. 이 판단에서 실수가 나면 담당자가 오히려 악성 메일을 전파하는 통로가 될 수 있었습니다.
- 산업군·부서·직급에 따라 그럴듯한 메일이 다르고, 대상자 맥락이 흐려지면 생성 품질이 흔들렸습니다.
- LLM이 만든 HTML이 훈련 대상자의 브라우저에서 그대로 렌더링되기 때문에, 생성 결과 자체가 공격 경로가 될 수 있었습니다.

**판단과 구현**

- 메일 유형별 필수 요소와 산업군·부서·직급·기술 이해도·위협 수준을 프롬프트의 독립된 입력 컨텍스트로 나눠, 조건 조합만으로 고객사별 시나리오를 만들 수 있게 했습니다.
- 원본 메일의 코드와 링크를 다루지 않으면 위험 자체가 사라진다고 보고, 메일 캡처 이미지에서 템플릿을 만드는 OCR 기반 흐름을 직접 제안해 도입했습니다. OCR로 메일을 해석하고, 보안 가이드라인에 따라 위협 링크를 제거한 뒤 UI 요소만 템플릿으로 재구성합니다. 메일 안에 HTML이 아닌 이미지로 들어간 영역은 템플릿을 먼저 만든 뒤 이미지 생성 API로 만든 이미지로 치환해, 이미지가 섞인 메일도 같은 흐름으로 처리했습니다.
- 범위 밖 요청을 시스템 프롬프트로 막는 것만으로는 우회될 수 있다고 보고, LLM이 만든 HTML은 신뢰할 수 없는 입력으로 취급해 sanitize와 인라인 CSS 속성 화이트리스트로 스크립트 실행 가능 요소를 코드에서 제거했습니다.

**결과**

- 원본 메일의 HTML과 링크가 템플릿에 들어갈 경로를 없애, 담당자가 악성 메일을 직접 검사하다 전파할 위험을 제거했습니다. 템플릿 등록도 수동 검사와 HTML 작성 대신 이미지 업로드 한 번으로 바뀌었습니다.
- 생성 결과가 어떤 내용이든 렌더링 전에 코드 수준에서 검증되도록 해, 31개 고객사 운영 환경에 AI 생성 콘텐츠를 안전하게 노출할 수 있게 했습니다.

### Mind-SAT AI 서버 고가용성 전환 | 2026 · 단독 수행

단일 OCI 인스턴스로 운영되던 AI 서버를 앱 코드 변경 없이 2대 인스턴스 풀 + Private Load Balancer 구조로 전환했습니다.

**문제와 제약**

- 인스턴스 하나가 죽으면 AI 기능 전체가 멈추는 단일 장애점이었고, 요청 기록·콜백·타임아웃 감시가 모두 인스턴스 로컬에 있어 장애 시 처리 중 요청도 함께 사라졌습니다.
- 운영 중인 인스턴스는 멈출 수 없어, 무중단으로 새 구조를 만들어야 했습니다.

**판단과 구현**

- 요청이 접수부터 콜백까지 한 인스턴스 안에서 끝나 공유 상태가 없다는 점을 근거로, 코드 재작성 없이 수평 확장할 수 있다고 판단했습니다.
- 처리 시간 대부분이 LLM 응답 대기라 CPU 지표가 부하를 반영하지 못하고, 실제 병목인 LLM rate limit은 증설로 풀리지 않아 오토스케일링 대신 고정 2대 풀을 택했습니다. 스케일-인이 처리 중 요청을 일상적으로 유실시키는 것도 이유였습니다.
- 운영 부트 볼륨을 클론해 무중단으로 골든 이미지를 만들고, 부팅만 하면 앱·스캐너·백신이 자동 기동되게 해 인스턴스를 언제든 교체·보충할 수 있는 소모품으로 만들었습니다.
- DB에 남은 진행 중 상태 플래그를 주기적으로 조회해 다시 처리하는 스케줄러를 구현해, 장애로 유실된 요청을 처리했습니다.

**결과**

- 테스트 환경에서 장애 복구를 검증한 뒤 운영 전환까지 마쳤습니다. 1대가 멈춰도 신규 요청은 끊기지 않고, 장애 감지부터 인스턴스 자동 보충·정상 복귀까지 1분 안에 이뤄집니다. 기존 수동 복구는 약 10분이 걸릴 수 있었습니다.
- 인스턴스가 중간에 죽어도 진행 중이던 요청을 다시 처리할 수 있게 되었습니다.

## 제품·플랫폼 개발 · 2023–2025

### 디자인 시스템·MCP 서버

React·TypeScript 공통 UI 라이브러리를 약 6개 사내 시스템에, 제품 디자인 시스템을 3개 제품에 적용했습니다.

AI가 존재하지 않는 props나 표준에 없는 색상·아이콘을 지어내는 문제를 막기 위해, AI가 도구로 호출해 참조하는 MCP 서버를 만들었습니다. 소스 코드의 Storybook 문서와 JSDoc 함수 설명을 레지스트리로 컴파일하고, 소스가 바뀔 때마다 자동으로 다시 컴파일해 문서와 실제 코드가 어긋나지 않게 했습니다. 프론트엔드 엔지니어 4명이 사용합니다.

### M365 Web Add-in 멀티테넌트 플랫폼 · Mind-SAT 프론트엔드 메인 개발

Mind-SAT 메일 신고와 Wrapsody eCo 문서 공유 앱을 하나의 React·TypeScript·Node.js 플랫폼에서 제품 모듈로 분리하고 Graph API 프록시·고객사별 설정을 공통화해, 고객사마다 서버를 두지 않는 멀티테넌트 구조로 추가 앱 개발 기간을 절반으로 줄였습니다.

Mind-SAT 프론트엔드(OTP/MFA, 교육·퀴즈, 관리자 통계)를 개발하고, 메일·AI·라이선스·백엔드 서버를 잇는 종단 E2E 테스트로 약 30분 걸리던 수동 검증을 약 8분으로 줄였습니다.

### 사내 업무 시스템·ERP 데이터 연동

인사·결재·고객 관리 시스템을 React·ASP.NET Core·MSSQL로 마이그레이션하고, 수동 쿼리로 반영하던 ERP 기준 데이터를 재실행 가능한 스케줄러 작업으로 전환했습니다.
